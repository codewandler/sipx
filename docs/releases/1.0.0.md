# sipx 1.0.0

This release freezes the bounded production audio endpoint described by the
[v1 endpoint-library contract](../specs/v1-endpoint-library.md). It supports both SIP endpoint
roles through one high-level Rust configuration and includes the declared call lifecycle,
signalling transports, encrypted media and NAT-reachability paths. It does not turn every
Experimental module or adjacent communications product into stable API.

Stable promotion follows the published rc.23 boundary. The content contract is complete, all five
roadmap evidence predicates hold under the product-boundary adoption policy, and the Supported Rust
surface is guarded mechanically against incompatible change.

## Install

```sh
cargo add sipx-call@=1.0.0
cargo install --locked --version '=1.0.0' sipx-cli
```

## Stable endpoint content

- **ICE and configured TURN relay.** The endpoint gathers host, server-reflexive and configured
  relayed candidates, owns allocation and permission lifetimes, nominates media paths, keeps
  completed generations alive and emits only valid nominated `remote-candidates` in later offers.
- **Encrypted production audio.** G.711, G.722, L16 and optional Opus are reachable from the call
  layer. SRTP, SDES and DTLS-SRTP are supported; both AEAD-GCM key sizes carry pinned positive and
  deliberately perturbed negative key-derivation evidence.
- **Complete endpoint call lifecycle.** Dial and answer roles share one opaque configuration for
  codecs, media security, ICE, identity and direction policy. Registration, transfer,
  renegotiation, cancellation and terminal outcomes have bounded owners.
- **Long-lived Outbound registration.** Registration refresh, negotiated keepalives, independent
  flow recovery, socket closure and task joining remain owned until cancellation.
- **Supported API compatibility.** A pinned rustdoc baseline covers 4,184 Supported paths across
  twelve publishable packages. A separate package-only consumer compiles against extracted
  archives rather than the live workspace.

## Adoption evidence

A separately maintained private downstream product consumes an immutable public sipx source in a
non-test production path. It uses no local path dependency, vendored sipx source, private fork,
workspace example or purpose-built adoption fixture. An authorized release review reproduced the
bounded validation and found no incompatible Supported-API break.

The product's identity, repository, source, architecture, infrastructure and operational details
remain private. The public record intentionally states only the release predicate and its result;
confidential evidence is retained outside this public repository.

## Verification boundary

The complete stable candidate must pass the repository's 55-step gate after all version, generated
documentation, API-baseline and stable-readiness artifacts are synchronized. Exact-SHA `main` CI
and Pages must then pass before the annotated `v1.0.0` tag is pushed. Protected publication remains
responsible for registry checksums, a registry-only consumer, the optional-feature installed CLI,
five native archives and SPDX documents, checksums, Pages probes and the non-draft stable release.

The interoperability evidence covers the two retained independent profiles across all five
released signalling transports. Media proofs cover the exact profiles and failure modes they name;
they are not universal claims about every peer, network, re-keying sequence or extension.

## Experimental surfaces and intentional omissions

The language-neutral application protocol and host bindings, browser-facing APIs, DSP graph,
speech providers, SIP-over-QUIC mapping and backend-specific handshake modules remain Experimental.
Their presence in a stable package does not make them part of the Supported compatibility promise.

The stable endpoint contract does not promise proxy, registrar, PBX, IMS, trunk, SBC, packaged
B2BUA or high-availability cluster roles; SIPREC, every event package or every SIP extension;
video, screen sharing, data channels or browser packaging; or speech, AI, acoustic processing and a
general DSP product. Later compatible releases may add behavior without changing this boundary.
