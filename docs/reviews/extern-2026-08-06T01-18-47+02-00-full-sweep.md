## Verdict

sipx RC.2 makes an unusually strong first impression for a young telephony stack: the documented
loopback call works verbatim, successful machine output is clean, recognized bad values receive
excellent explanations, every native codec negotiated correctly, hold/resume worked end to end,
and the browser-audio profile produced a real native Opus/DTLS-SRTP/ICE call.

The review also found several ordinary product paths where the shipped command does not preserve
the contract its own help and reports imply. The most consequential are call lifecycle handling,
hostname reachability, timeout enforcement, refusal signaling when no codec is shared, the default
load-tool pairing, and the automation contract of `scenario`. These are not protocol-core
speculation: each was observed through the built RC.2 binary, usually with a second process, exit
status, packet capture, counters, or wall-clock measurement.

This was intended as a full sweep, but it is not one. Concurrent builds exhausted the shared
RAM-backed temporary filesystem. The Rust-library newcomer exercise, application-SDK integration,
and general performance/resource tracks were stopped rather than reported from incomplete data.

## Findings

### 1. [High] A confirmed call does not follow the peer's lifecycle

- Confidence: `CONFIRMED`
- Reproduction: run `answer --duration 10`, connect with `dial --duration 2`, and measure both
  processes; separately terminate the dialer during a 20-second call while capturing signaling.
- Observed: the dialer sent a clean BYE at about two seconds, but `answer` remained alive for its
  full local ten-second duration. When the dialer was terminated, it emitted no BYE and no JSON;
  the answer side again retained the dialog until its own duration elapsed. The call commands do
  not drive the library's complete serving loop while media exchange is active.
- Expected: the live call should consume in-dialog requests, end when the far side hangs up, and
  perform orderly local teardown on an interrupt.
- Consequence: channels and media remain allocated after the logical call ends; an orchestrator
  killing the command receives no terminal machine record.
- Evidence: `crates/sipx-cli/src/answer.rs`, `crates/sipx-cli/src/dial.rs`, and the public library
  guide's requirement to keep serving a confirmed call.

### 2. [High] Ordinary CLI targets cannot use hostnames

- Confidence: `CONFIRMED`
- Reproduction:

  ```text
  sipx dial sip:x@localhost:15080
  sipx dial sip:x@example.com:5060
  sipx register sip:alice@example.com
  ```

- Observed: `dial` requires a literal IP address and port. `register` accepts the hostname-shaped
  AOR but reports that name resolution is not wired into the command and asks for `--target`; that
  target also requires an address form rather than resolving a hostname.
- Expected: a user-agent command should be able to call or register to the named host in an AOR, or
  clearly present literal-address operation as a product limitation before invocation.
- Consequence: registering against an ordinary named PBX and using a URI hostname for TLS identity
  are unreachable from the CLI without external resolution and manual address injection.
- Evidence: target derivation in the RC.2 `dial`, `register`, and scenario command paths.

### 3. [High] A no-common-codec answer sends no final SIP response

- Confidence: `CONFIRMED`
- Reproduction: start `answer` with only L16 and dial it with a non-overlapping codec set while
  capturing the answer side.
- Observed: the answerer reported `{"status":"failed","error":"no codec in common"}`, but its
  counters recorded one message in and zero messages out. The caller waited and ultimately reported
  a timeout. No 488 response appeared on the wire.
- Expected: reject the invitation with a final response describing the unacceptable session.
- Consequence: a deterministic capability mismatch looks like packet loss or an unavailable peer,
  delays callers, and invites pointless retries.
- Evidence: packet capture and `messages_in: 1`, `messages_out: 0` from the answer-side counters.

### 4. [High] `register --timeout` does not enforce its advertised budget

- Confidence: `CONFIRMED`
- Reproduction:

  ```sh
  sipx register sip:alice@example.com \
    --target 127.0.0.1:15999 --timeout 3 --json
  ```

- Observed: the command returned after about 32 seconds, not three, with `status: "timeout"`.
- Expected: the command should give up near the requested three-second budget.
- Consequence: scheduled registration checks and automation can block for an order of magnitude
  longer than configured.
- Evidence: repeated wall-clock measurement against a non-answering local target.

### 5. [High] `load` fails against `load-responder`'s documented default mode

- Confidence: `CONFIRMED`
- Reproduction: start the bounded responder without `--mode` and run:

  ```text
  sipx load-responder --local 127.0.0.1:15093 \
    --max-active 32 --cleanup 10 --duration 120 --json
  sipx load sip:x@127.0.0.1:15093 --calls 20 --rate 10 \
    --concurrency 8 --call-duration 1 --json
  ```

- Observed: the default `signalling` responder creates no media session, while `load`
  unconditionally attempts media playback and treats failure as fatal. The run stopped after one
  attempted call, reported `status: "interrupted"`, exited 0, and produced no diagnostic even at
  high verbosity. Selecting `generated-media` allowed the run to proceed.
- Expected: the paired commands' defaults should interoperate, or the mismatch should be refused
  before the run with a nonzero, actionable failure.
- Consequence: the documented bounded-load example can appear operator-interrupted after doing no
  useful measurement, while automation sees success.
- Evidence: `crates/sipx-cli/src/load.rs` media playback/stop path and the responder's default-mode
  contract.

### 6. [High] `scenario`'s documented input shape and process result do not support automation

- Confidence: `CONFIRMED`
- Reproduction: send the object shape described by help, then the actual accepted form; separately
  send only malformed or refused commands.
- Observed: help says each object has an `id` and one command, which naturally yields
  `{"id":"1","dial":{...}}`; the parser rejects that because it requires a string `command` (or
  `do`) field with parameters at the top level. The working form is
  `{"id":"1","command":"dial","uri":"..."}`. Every command refused, invalid JSON, and a failed
  dial all still ended with process exit 0. `wait_for` also requires `timeout_ms`, which help did not
  state during the reviewed run.
- Expected: the built-for-automation surface should document one executable frame and return a
  failing process status when the input stream achieves no successful operation.
- Consequence: consumers must read source to discover the protocol, and supervisors cannot use the
  process status to distinguish success from total refusal.
- Evidence: `crates/sipx-cli/src/scenario.rs` command extraction and direct NDJSON runs.

### 7. [Medium] Unknown and misspelled flag names are silently ignored

- Confidence: `CONFIRMED`
- Reproduction:

  ```text
  sipx dial sip:x@127.0.0.1:15999 --duation 2 --timeout 1
  sipx dial sip:x@127.0.0.1:15999 --not-a-flag
  sipx dial sip:x@127.0.0.1:15999 --json=yes
  ```

- Observed: all three proceeded. The typo used the default duration, and `--json=yes` silently
  selected text output rather than the structured output a script was expecting.
- Expected: reject unknown options as usage errors and name the offending token.
- Consequence: configuration mistakes alter behavior without a local diagnostic; the JSON case
  moves the failure into a downstream parser.
- Evidence: RC.2's shared argument parser validates recognized valued flags but skips other names.

### 8. [Medium] Dial timeouts consistently overshoot by about two seconds

- Confidence: `CONFIRMED`
- Reproduction: dial a non-answering UDP target with `--timeout` set to 1, 2, 3, 5, and 8 seconds.
- Observed:

  | Requested | Wall time |
  |---:|---:|
  | 1 s | 3.03 s |
  | 2 s | 4.02 s |
  | 3 s | 5.02 s |
  | 5 s | 7.01 s |
  | 8 s | 10.01 s |

- Expected: the user-visible give-up budget should bound the command, including cancellation and
  cleanup, or the extra cleanup allowance should be separately documented.
- Consequence: short operational budgets are exceeded by 25–200 percent while the error still says
  the configured threshold was the elapsed bound.
- Evidence: repeated wall-clock measurements; the constant tail is consistent with post-timeout
  invitation cancellation.

### 9. [Medium] A real Firefox browser could not complete the browser-audio proof

- Confidence: `CONFIRMED` for the interop failure; the exact candidate-level cause is `PLAUSIBLE`
- Reproduction: run `tests/browser-audio/run.sh` with its documented command/template override
  points directed at geckodriver and a Firefox capability file, using a trusted test CA.
- Observed: WebDriver started, the page loaded, WSS/TLS completed, ICE began, and SIP/SDP reached
  sipx. sipx then failed with `Profile(RtcpMuxRequired)`; the browser recorded
  `ice_started: true`, `nominated: false`, and zero RTP packets.
- Expected: an offer with `a=rtcp-mux` from a mainstream browser should pass the audio profile when
  unused component candidates are also present.
- Consequence: the shipped profile worked native-to-native but did not interoperate with the second
  browser engine exercised in this review.
- Evidence: the live geckodriver run and the candidate-component rejection in
  `crates/sipx-sdp/src/browser_audio.rs`. Raw SDP was not captured, so the conclusion that an RTCP
  component-2 candidate triggered the exact branch remains a bounded inference.

### 10. [Medium] DTMF was negotiated and sent but no receive event arrived

- Confidence: `CONFIRMED`
- Reproduction: establish two scenario-controlled calls, send `1234` with `send_dtmf`, and wait on
  the receiving actor for `call.dtmf` with a finite deadline.
- Observed: both SDP directions negotiated `telephone-event/8000` payload 101; the sender completed
  `send_dtmf`; the receiver's event wait expired without a DTMF event. The same harness then proved
  hold and resume events successfully in both directions.
- Expected: negotiated digits sent through the public scenario command should surface through its
  typed event stream.
- Consequence: IVR-style scenario tests cannot observe digits even though negotiation and sending
  report success.
- Evidence: correlated scenario transcripts and the negotiated SDP capture.

### 11. [Medium] Transport refusal is classified as a timeout

- Confidence: `CONFIRMED`
- Reproduction:

  ```sh
  sipx dial sip:x@127.0.0.1:15999 --transport tcp --timeout 5 --json
  ```

- Observed: a refused TCP connection returned in roughly 20 ms as
  `{"status":"timeout","error":"no final response to the INVITE"}` with timeout exit code 5.
- Expected: an immediate, definitive connect failure should be `failed` with exit 1 and preserve
  the transport cause.
- Consequence: retry policy receives the wrong signal and may spin against a closed port.
- Evidence: local closed-port reproduction and elapsed time far below the configured timeout.

### 12. [Medium] Troubleshooting places global-looking options where the CLI rejects them

- Confidence: `CONFIRMED`
- Reproduction: execute the troubleshooting page's leading command, beginning
  `sipx -vv dial ...`, verbatim.
- Observed: the root parser treated `-vv` as the command, printed help, reported
  `unknown command: -vv`, and exited 2. The same placement issue affected `--json`; both options
  worked after the subcommand.
- Expected: examples should use the placement accepted by the binary, or help should state that
  these are subcommand-local rather than global.
- Consequence: the first instruction on the page intended to unblock a confused user fails before
  attempting a call.
- Evidence: `website/docs/troubleshooting.md`, CLI help, and verbatim execution.

### 13. [Medium] Recording destination errors are discovered after the call

- Confidence: `CONFIRMED`
- Reproduction: complete a short call while setting `--record` to a path in a nonexistent or
  unwritable directory.
- Observed: the call connected and ran, then the command failed when writing the recording. In
  contrast, invalid `--play` input was checked before signaling.
- Expected: validate that the recording destination can be created before spending the one chance
  to capture a call.
- Consequence: a long or non-repeatable call can complete successfully and lose its recording only
  at teardown.
- Evidence: connected loopback call with a failing destination path.

### 14. [Low] Structured browser-audio output contains a duplicate key

- Confidence: `CONFIRMED`
- Reproduction: complete a native browser-audio profile call with `--json` and inspect keys without
  collapsing duplicates.
- Observed: `media_profile` appeared twice, once in the requested report and once in the negotiated
  report.
- Expected: each JSON object key should be unique.
- Consequence: ordinary parsers retain one value, but strict or duplicate-rejecting consumers fail
  on an otherwise successful call report.
- Evidence: `crates/sipx-cli/src/media.rs` requested and negotiated report writers.

## What works well

- The README quickstart worked verbatim. The release build completed, the two CLI processes formed
  a real loopback call, both emitted one-line JSON, and both exited 0.
- Error messages for recognized invalid values were exceptional: they named the option, echoed the
  bad value, enumerated valid values, and often explained the practical cause such as an unset shell
  variable expanding to an empty string.
- stdout remained clean JSON even at high verbosity; logs stayed on stderr. Bind failures and
  missing-feature failures were specific and actionable.
- Documented exit codes for normal dial/answer outcomes matched direct tests: success, failure,
  usage, rejection, timeout, and busy.
- `scripts/check-cli-reference.py --check` confirmed that all eight command helps and five versioned
  JSON contracts matched the generated reference.
- PCMU, PCMA, L16, and Opus all negotiated with the expected clock rates in native loopback calls.
- Hold and resume worked through the scenario surface, and the remote actor received both events.
- The browser-audio profile worked native-to-native and reported Opus at 48 kHz, DTLS-SRTP, host
  ICE, a nominated candidate pair, running media, and plausible loopback quality.
- Browser/profile feature-gate errors clearly stated the missing build feature or transport
  prerequisite. The public browser-proof docs candidly name the supported browser and disclaim a
  general browser/WebRTC stack.
- The load responder requires explicit finite admission, active-call, and cleanup bounds, which
  prevents accidental unbounded load generation.
- Capture counters expose useful operational facts including unsent dialog messages,
  retransmissions, parse failures, shedding, capture loss, and send failures.

## Environment and methodology notes

Five review tracks were initially fanned out concurrently. Their Rust builds filled a 32 GiB
RAM-backed `/tmp` to the point that file creation and even command-wrapper output became unreliable.
Three heavy tracks were stopped, their scratch build directories removed, and only results already
printed or subsequently reproduced on a stable shell were retained. The external-review command
derived from this session therefore runs heavy tracks sequentially by default.

Several harness observations were corrected during the run:

- a shell background job inherited ignored SIGINT, initially making the CLI appear to ignore the
  signal; a Python harness restored default dispositions and replaced that result;
- pipeline status initially masked the real exit code of one command; direct execution replaced it;
- an empty peer-book fixture was caused by temporary-filesystem exhaustion; the book behavior was
  rechecked after recovery and is not a finding; and
- broad process matching could select the invoking shell, so later cleanup used exact PIDs/names.

The fresh review clone was clean when the run ended. No source, story, board, changelog, or release
artifact was changed as part of the external review.
