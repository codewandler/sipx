## Verdict

The advertised core works, and it works well: the pinned registry install is real and fast, the
published release archives verify, and the README's loopback quick start produces a genuine
bidirectional G.711 call with correct WAV artifacts on the first try. Argument-value diagnostics,
exit-code discipline, and the JSON contract are unusually well built.

One defect dominates the assessment: **all three CLI call surfaces (`dial`, `answer`, `scenario`)
never process inbound in-dialog SIP requests during an established call.** A BYE from the far end
is neither answered nor acted upon, so a remote hangup is invisible; the call runs to its local
`--duration` and the reported `duration_ms` overstates the real call length (measured 20001 ms for
a call the peer ended after 2 s). The same cause leaves the INVITE 2xx retransmitting for the life
of the call because the ACK is never dequeued. The `sipx-call` library does this correctly through
its documented `serve()` loop — verified answering a BYE in 1 ms — so this is a CLI integration
defect rather than a flaw in the SIP core. For a product whose stated purpose is a scriptable phone
with machine-readable call records, this affects call-duration reporting, hangup detection, and how
the peer sees every call.

Secondary themes: unknown command-line flags are silently discarded (a typo'd `--record` loses a
recording with exit 0 and no warning), and `dial`/`answer` have no signal handling, so an
interrupted call never sends a BYE.

Nothing here suggests the release is broadly unsound. It is a narrow, high-consequence integration
gap in an otherwise carefully made product.

## Findings

### 1. [High] `dial`, `answer` and `scenario` ignore inbound BYE: remote hangup is undetected and reported call duration is wrong

- Confidence: `CONFIRMED`
- Reproduction (pure sipx-to-sipx, two documented commands, no custom harness):

  ```sh
  # terminal one — answerer told to stay up for 20 s
  sipx answer --local 0.0.0.0:5095 --wait 30 --duration 20 --once --json
  # terminal two — caller hangs up after 2 s
  sipx dial sip:you@127.0.0.1:5095 --duration 2 --timeout 6 --json
  ```

- Observed: the caller reports `duration_ms: 2001` and exits at ~2 s. The answerer stays in the
  call for the full 20 s and reports:

  ```json
  {"status":"answered","caller":"<sip:sipx@127.0.0.1>;tag=4377faaab42df9d4",
   "media_advertised":"127.0.0.1","media_bound":"127.0.0.1:57834",
   "duration_ms":20001,"samples_recorded":0,"heard_audio":false}
  ```

  Answerer wall time 22.32 s, exit 0. Verified against an independent Python UAC on the wire: a
  well-formed in-dialog `BYE` (`CSeq: 2 BYE`, Request-URI = the peer's advertised Contact, matching
  Call-ID and both tags) received **no response of any kind** within a 6 s observation window, and
  the answerer was still running 20 s later. The same holds in the UAC role: an independent UAS sent
  `BYE` at t=2.098 s to `sipx dial`'s Contact; it was never answered, the call continued, and sipx
  reported `duration_ms: 4001` for its own full `--duration`. `scenario` behaves identically — a
  remote BYE at t=2.19 s produced no response and no event; `call.ended {"cause":"hangup"}` appeared
  only at t=7.32 s when stdin closed, i.e. sipx's own local hangup mislabelled as the call's end.
- Expected: RFC 3261 §15.1.2 — a UAS receiving BYE within an existing dialog responds `200 OK` and
  terminates the session (`481` for an unknown dialog); silence is not a permitted outcome. The
  project's own published example asserts the intended behaviour: "this answers a BYE and stops the
  media when the caller hangs up".
- Consequence: a remote hangup is invisible to every CLI call surface. Reported `duration_ms`
  measures the local timer, not the call — 20001 ms for a 2 s call, a 10× overstatement — so any
  metering, billing, or CI assertion built on the documented JSON is wrong whenever the far end
  hangs up first. Media keeps flowing to a peer that has left, `answer --duration 300` holds a slot
  for five minutes after the caller is gone, and the peer's BYE transaction fails (its own
  retransmissions go unanswered until it gives up), which real PBXs log or alarm on.
- Evidence: the cause is visible in the shipped code once reproduced. `crates/sipx-cli/src/answer.rs:218`
  joins four media futures all bounded by `duration`; the `incoming` request stream is read only at
  `crates/sipx-cli/src/answer.rs:148`, to wait for the initial INVITE, and never again.
  `crates/sipx-cli/src/dial.rs:172` binds it to `_incoming` and discards it. No inbound in-dialog
  request is dequeued while a call is up. **The library is not affected** — see finding 2's contrast
  and [What works well](#what-works-well).

### 2. [Medium] The INVITE 2xx retransmits for the whole call because the ACK is never dequeued

- Confidence: `CONFIRMED`
- Reproduction: an independent Python UAC sends INVITE, then a correct in-dialog ACK, then waits.

  ```sh
  sipx answer --local 0.0.0.0:5086 --wait 30 --duration 120 --once --json   # in another terminal
  python3 uac.py 5086 2.0 6.0
  ```

- Observed: ACK sent at t=0.001 s; `sipx` retransmitted `SIP/2.0 200 OK` (`CSeq: 1 INVITE`) at
  t=0.501, 1.502, 3.503 and 7.504 s — intervals 0.5/1/2/4 s, the T1 doubling capped at T2 — and
  continued for as long as observed. The same pattern appears in sipx-to-sipx runs read from
  `sipx --capture` with TShark, where the answerer's own capture records receiving the ACK at
  t=0.0004 s and still retransmits at 0.501 s. Its counters file for a 2 s call reports
  `messages_out: 8, messages_in: 4, retransmissions_sent: 2`.
- Expected: RFC 3261 §13.3.1.4 — receipt of the ACK stops 2xx retransmission.
- Consequence: every answered call sends a growing series of duplicate `200 OK`s for its entire
  duration. The peer must absorb and re-ACK each one; switches that treat repeated 2xx as an
  ACK-timeout symptom will log or alarm, and signalling volume per call is several times the
  necessary minimum.
- Evidence: same root cause as finding 1 — the transaction layer only advances when the application
  polls `incoming`. This is confirmed by the contrast in the library consumer: it retransmitted the
  2xx exactly once, at t=0.609 s, during the `record_until_idle` phase before `serve()` begins
  polling, and never again once `serve()` ran. The sans-IO core appears correct; it is simply not
  being fed.

### 3. [Medium] Unknown command-line flags are silently discarded, so a typo runs a different command than requested

- Confidence: `CONFIRMED`
- Reproduction:

  ```sh
  sipx dial sip:x@127.0.0.1:5099 --timeout 1  --json   # correct spelling
  sipx dial sip:x@127.0.0.1:5099 --timeuot 1  --json   # one transposition
  ```

- Observed: the correct form exits 5 in 3.01 s with `no answer within 1s`. The typo exits 5 in
  22.00 s with `no answer within 20s` — both the unknown flag and its value were dropped and the
  command ran on the default. No warning on either stream. Reproduced identically on the registry
  build and the release archive, and on every subcommand tried (`dial`, `answer`, `peers`,
  `devices`). The damaging variant, against a live answerer:

  ```sh
  sipx dial sip:you@127.0.0.1:5101 --recrod typo.wav --duration 2 --timeout 5 --json
  ```

  exits **0** with `{"status":"answered",…,"duration_ms":2006,…}`, no `recording` field, no
  `typo.wav`, and nothing on stderr. The correctly spelled run emits `"recording":"good.wav"` and
  creates the file.
- Expected: an unrecognised option is a usage error (this CLI already reserves exit 2 for exactly
  that). The product states the principle itself when rejecting a valueless flag: "A flag in final
  position is not an absent one — reading it as absent would run this command on a default that was
  not asked for." A misspelled flag is the same hazard. No published document states an
  ignore-unknown-flags policy; searches of the README, CLI reference, getting-started and
  troubleshooting pages found none.
- Consequence: silent data loss and silent behaviour changes in scripts. `--recrod` records nothing
  and still exits 0, so a pipeline reports success and produces no artifact; a typo'd `--duration`
  or `--timeout` silently substitutes a default, changing call length and run time.

### 4. [Medium] `dial` and `answer` have no signal handling, so an interrupted call sends no BYE and emits no report

- Confidence: `CONFIRMED`
- Reproduction: spawn from a harness with default child signal dispositions (not a shell background
  job), let the call establish against an independent UAS, then signal.
- Observed: `dial` interrupted mid-call exits `-15` (SIGTERM) and `-2` (SIGINT) — killed by the
  default disposition — with empty stdout and stderr. The independent UAS transcript shows
  `INVITE / 200 OK / ACK` and then **no BYE**: `BYE seen by peer after interrupt: NO`. `answer`
  behaves the same while waiting for a call. Reaction time 0.00 s in all four cases, i.e. no handler
  ran. By contrast, `load-responder` **does** handle SIGINT gracefully (see finding 5).
- Expected: a phone that is interrupted should clear the dialog it created (BYE, or CANCEL for a
  pending INVITE), and a `--json` run should emit an outcome record so a supervisor learns how it
  ended.
- Consequence: Ctrl-C or any orchestrator stop leaves the peer holding an established dialog with
  media pointed at a dead process; combined with finding 1, neither side ever releases it. No JSON
  record is produced for the interrupted run, so automation sees only a signal exit code.

### 5. [Low] `load-responder` honours the documented interruption contract for SIGINT but not SIGTERM

- Confidence: `CONFIRMED`
- Reproduction: start `sipx load-responder --local 127.0.0.1:5121 --max-active 8 --cleanup 3
  --duration 60 --json`, wait 2 s, then send one signal.
- Observed:

  | Case | Exit | stdout lines | Terminal `sipx.load-responder.v1` summary |
  |---|---|---|---|
  | natural completion (`--duration 2`) | 0 | 2 | yes, `status=completed` |
  | SIGINT after 2 s | 0 | 2 | yes, `status=interrupted` |
  | SIGTERM after 2 s | -15 | 1 | **no** |

- Expected: the CLI reference states "Admission stop, interruption and internal error cancel and
  join every owned dialog before reporting", and that in `--json` mode the terminal summary is the
  expected final stdout line.
- Consequence: process supervisors (systemd, Kubernetes, `docker stop`, most CI runners) send
  SIGTERM, so the measurement run they stop produces no summary and a non-zero-looking signal exit —
  exactly the path the documented contract promises to cover. SIGINT, the interactive case, works.

### 8. [Low] `--record` failures surface only after the call, unlike `--play`

- Confidence: `CONFIRMED`
- Reproduction: against a live answerer, `sipx dial sip:you@127.0.0.1:5104 --record ro/out.wav
  --duration 2 --timeout 5 --json`, where `ro/` is mode 500.
- Observed: exit 1 after 2.02 s (the whole call ran first) with
  `{"status":"failed","error":"ro/out.wav: Permission denied (os error 13)"}`. By contrast a missing
  `--play` input is rejected before dialling: exit 2,
  `{"status":"usage","error":"/nonexistent/nope.wav: No such file or directory (os error 2)"}`.
- Consequence: an unwritable recording target is discovered only after the call completes, so the
  recording of a long call is lost at the end rather than refused in the first millisecond. The
  error message itself is clear and correctly classified.

### 9. [Low] `--json` is accepted but ignored by `version`, and feature-gate errors depend on the peer answering

- Confidence: `CONFIRMED`
- Reproduction and observations:
  - `sipx version --json` → exit 0, stdout `sipx 1.0.0-rc.2`, which is not JSON, though the global
    option is documented as "Report results as JSON on stdout". `sipx version --json extra` also
    ignores the stray positional. (`version` is not among the five schema'd contracts in the CLI
    reference, so this is a global-flag consistency gap rather than a broken contract.)
  - `sipx dial … --codec opus` on a build without the `opus` feature gives an excellent message
    **when a peer answers** — exit 2,
    `{"status":"usage","error":"codec \`opus\` requires a build with the \`opus\` feature"}` — but
    against an unreachable peer the same command instead times out (exit 5, `no answer within 1s`)
    and never mentions the build limitation.
- Consequence: `sipx version --json | jq` fails in scripts. The feature-gate diagnostic is
  excellent but arrives late, so the clearest explanation of a mis-built binary is the one a user
  reaching an unreachable host never sees.
- Correction to an earlier reading in this review: my first probe of `--profile browser-audio`,
  `--media-security dtls-srtp` and `--codec opus` used an unreachable port and appeared to show the
  feature gates being ignored entirely. They are not — the timeout simply pre-empted them. The
  behaviour above supersedes that reading.

### 10. [Low] `sipx load` cannot drive `sipx load-responder` in the responder's default mode, and reports the aborted run as exit 0

- Confidence: `CONFIRMED`
- Reproduction:

  ```sh
  sipx load-responder --local 127.0.0.1:5112 --max-active 64 --cleanup 5 --duration 60 --json
  sipx load sip:load@127.0.0.1:5112 --rate 5 --concurrency 2 --calls 4 --call-duration 1 --timeout 5 --json
  ```

- Observed: the load run stops after a single call —
  `{"status":"interrupted","outcomes":{"attempted":1,"connected":0,"failed":1,…},"response_codes":{}}` —
  and **exits 0**, with nothing on stderr and, with `-v`, no log output at all. A plain
  `sipx dial` against the same responder explains it:
  `{"status":"failed","error":"sdp: missing the o= line"}`. The responder's default `signalling`
  mode answers without SDP, which the CLI reference does state ("The default creates no SDP or
  media session"). Adding `--mode generated-media` makes the pair work perfectly (see
  [What works well](#what-works-well)).
- Expected: the two shipped load tools are presented as a pair — the readiness envelope is even
  named `sipx.comparative-load.ready.v1` with a `role` field — so the default combination working
  is a reasonable expectation; failing that, the failure should name the cause and not exit 0. The
  word "interrupted" also misdescribes a run that no one interrupted.
- Consequence: the first attempt at the load feature aborts after one call and reports success to
  CI. Neither command's `--help` mentions that the peer must supply SDP, so the diagnosis requires
  the CLI reference plus a separate `dial` experiment.

### 11. [Low] `answer -v` and `load -v` produce no call progress, and `scenario --help` implies a command shape that is refused

- Confidence: `CONFIRMED`
- Observed:
  - The README documents `-v` as "Log a call's progress to stderr: what was dialled, what answered,
    who called, how it ended (INFO)". For a completed 8 s answered call, `sipx answer … -v` logged
    exactly one line — `INFO sipx::answer: waiting for a call address=0.0.0.0:5096 within=25s` —
    with nothing about who called or how it ended. `sipx load … -v` logged nothing at all.
    `dial -v` is the counter-example and behaves as documented:
    `calling` / `answered … setup=594.111µs` / `hung up … elapsed=4.023071354s`.
  - `scenario --help` says "Every object has a string `id` and one of: dial, accept, reject, …",
    which reads as `{"id":"a","dial":{…}}`. Every such form is refused with
    `{"type":"scenario.command.refused","message":"command must be a string"}`. The working shape is
    `{"id":"a","command":"dial","uri":"sip:…"}` (`target` also accepted), discoverable only by
    experiment or by noticing `command` in the reference's field table. No published page shows a
    complete command line for any of the 14 v1 commands.
- Consequence: `-v` is the documented way to see what a call did, and for the answering side it
  shows nothing. An integrator writing to the `sipx.app.v1` contract cannot construct a single valid
  command from the published documentation.
- Correction: an earlier probe of mine appeared to show that malformed JSON and unknown commands
  produce no refusal envelope. That was my harness closing stdin immediately, which triggers the
  documented EOF shutdown before the command is processed. With stdin held open, refusals arrive
  exactly as documented, with precise messages including a line and column for bad JSON. The
  refusal contract holds.

## What works well

- **The pinned install is real.** All twelve `sipx-*` crates are published at exactly
  `1.0.0-rc.2`, matching the README byte for byte. `cargo install --locked --version =1.0.0-rc.2
  sipx-cli` succeeded in **45.5 s**, and `sipx version` printed `sipx 1.0.0-rc.2`.
- **The release artifacts verify.** The getting-started `curl`/`SHA256SUMS`/`sha256sum --check`/`tar`
  recipe ran verbatim with every step exiting 0 —
  `sipx-1.0.0-rc.2-x86_64-unknown-linux-musl.tar.gz: OK` — yielding a 9.5 MB static-pie musl binary
  (8.1 MB stripped) plus licences and a `build-manifest.json` recording `release_sha`,
  `rustc 1.88.0`, `features: []` and `source_date_epoch`. All five advertised targets are present
  with SPDX sidecars.
- **The README quick start works on the first attempt, with real audio.** Both sides exited 0; each
  recorded 15680 frames (1.96 s) with `heard_audio: true`; both WAVs were mono/16-bit/8000 Hz,
  matching the documented negotiated G.711 clock; `duration_ms` was 2001 for a requested 2 s.
- **Value diagnostics are the best part of the CLI.** Empty and missing values are refused with
  reasoning a user can act on: `--duration ''` →  "No flag here has a meaningful empty value, and an
  unset shell variable expands to exactly this, so it is refused rather than read as absent";
  `--duration` in final position → "A flag in final position is not an absent one". Range errors
  name the exact bounds (`must be a whole number of seconds from 0 through 4294967295, not "abc"`),
  and `--transport carrier-pigeon` lists the valid set.
- **Stream and exit-code discipline hold.** Results on stdout, logs and failure envelopes on stderr,
  one JSON object per line, exactly as the CLI reference specifies — including the documented
  detail that failures emit `{"status":…,"error":…}` on stderr. Distinct codes were observed in
  practice: 0 success, 1 failed, 2 usage, 5 timeout. Bare `sipx` prints help to stdout and exits 0,
  while `sipx --json` with no command correctly exits 2 — a deliberate and sensible distinction.
- **The library does the thing the CLI misses.** The external consumer built from the published
  answer-a-call example answered my independent UAC's BYE with `200 OK` in **1 ms**, terminated the
  session, printed "the call ended" and exited on its own. It also received independent RTP exactly:
  30 PCMU frames × 160 samples reported as "heard 4800 samples". The documented `serve()` loop is
  correct and its doc comment describes its behaviour accurately.
- **Adoption cost is modest.** 164 crates in the dependency graph, a clean build with no warnings
  from the consumer's own code, and clear compiler-visible errors when a dependency is missing.
- **`load` is well engineered once correctly paired.** 100 calls at rate 20/concurrency 10 in
  generated-media mode: `attempted: 100, connected: 99, timed_out: 1, failed: 0`, accounting
  internally consistent (`connected+rejected+timed_out+failed == attempted`), `peak_concurrency: 10`
  exactly at the limit and never above, monotonic `setup_ms` percentiles (p50 0, p95 1, p99 2),
  `response_codes {"200": 99}` and `media.snapshots: 99` both consistent with the connected count,
  `mean_mos 4.40` with zero loss and jitter. **Peak RSS 12.4 MB** for ten concurrent calls. Every
  structural field the CLI reference requires for `sipx.load.v1` was present. The observed 10.35
  calls/s is the concurrency limit doing its job (ten slots × 1 s calls), not a missed rate.
- **Fast and small.** `sipx version` cold start: min 1.3 ms, p50 1.4 ms, max 2.4 ms over 20 runs;
  `dial --help` p50 1.5 ms.
- **Good failure messages elsewhere.** `devices` on a build without the feature: "audio devices
  require a build with the `device-audio` feature". `peers` with no peer book names the exact path.
  `--record` of a silent call produces a valid 44-byte WAV with `samples_recorded: 0` and
  `heard_audio: false` — precisely the documented "successfully completed silent call" contract.
- **`--capture`, `--counters` and `--stats` all work as advertised** and were load-bearing for this
  review: the pcapng was readable by TShark unmodified, and the counters file is a genuinely useful
  diagnostic (it is what first quantified finding 2).
- **The scenario refusal contract is solid** once stdin is driven correctly: precise messages,
  correct `id` echo, a line/column for malformed JSON, and a clean versioned envelope
  (`contract: sipx.app.v1`, monotonic `seq`). `call.answered` arrived 0.3 s after the command.
- **Documentation is candid about boundaries.** The fit table, the explicit non-goals (no proxy,
  registrar, PBX, TURN, video, data channels, general WebRTC), and the "When the far end vanishes"
  section on RFC 4028 session timers are honest and useful. Notably, that section handles the
  *harder* case — a peer that vanishes without a BYE — which makes finding 1 the more surprising.

## Not covered

- **Browser interoperability — not attempted.** The claim is narrow and explicitly scoped (a
  fail-closed `browser-audio` composition profile behind the `opus` and `dtls` features, not a
  general WebRTC stack), and testing it honestly needs a real browser driven by WebDriver. Neither
  `chromedriver` nor `geckodriver` is installed, and a WSS path needs a trusted certificate plus a
  rebuild with `--features opus,dtls`. Free space on the scratch filesystem fell from 35.4 GiB to
  10.6 GiB during this review through activity outside it, so I declined to start another large
  build. No conclusion should be drawn about browser interoperability from this review; the
  project's own native-browser audio proof remains uncorroborated here.
- **MSRV `rustc 1.88` — not verified.** Only 1.97.0 was available, and installing a 1.88 toolchain
  writes to the user-global `~/.rustup`, which this review's isolation rules forbid. The release
  archive's `build-manifest.json` does independently record `rustc 1.88.0`.
- **Registration, TLS, WSS, QUIC and mutual TLS — not exercised.** No registrar, account
  credentials, or certificate authority was available, and I did not create credentials for a
  third-party service. `register` was therefore only exercised through its argument surface.
- **`device-audio` — not exercised.** The reviewed builds carry no optional features; `devices`
  correctly reported the feature was absent.
- **Opus, SRTP/SDES, DTLS-SRTP, ICE/STUN, transfer, hold/resume, early media, two-leg coupling,
  event packages (SUBSCRIBE/NOTIFY/PUBLISH), dialog persistence, and the `sipx-app` host and its
  webhook/realtime bindings** — outside the bounds of this pass. `scenario` was exercised only far
  enough to establish findings 1 and 11; its `play`, `transfer`, `hold`, `send_dtmf` and `wait_for`
  commands were not tested, partly because their payload shapes are undocumented (finding 11).
- **Security — excluded by scope**, and not assessed in any form.
- **Long-session memory behaviour** was not measured; the longest observed process lifetime was
  about 22 s. Peak RSS is reported only for the bounded 100-call load.
- **Comparative performance claims** were not attempted: the machine was under external load and
  disk pressure throughout, which makes any cross-stack number untrustworthy.

## Environment and methodology notes

- **Two binaries, both by absolute path.** A pre-existing `sipx` sits at `~/.cargo/bin/sipx` on
  this machine. It was never invoked: every command in this report used either
  `<scratch>/prebuilt/bin/sipx` (release archive) or `<scratch>/install/root/bin/sipx`
  (`cargo install --root <scratch>`). Findings 1, 2 and 3 were reproduced on both builds.
- **The reviewed revision is the released tag, not the working copy.** The clone is
  `5dab4ef` / `v1.0.0-rc.2`, and it was verified clean (`git status --porcelain` empty) at the end of
  the run. Uncommitted work in the invoking checkout was deliberately excluded and never read.
- **Harness corrections made during the review**, all of which changed a conclusion:
  1. My first attempt to prove finding 3 compared `--duration 2` against `--duratoin 2` and found no
     difference in wall time. That test could not discriminate — `--duration` is the in-call length
     while `--timeout` bounds the answer wait, so both runs hit the same 20 s default. Re-run against
     `--timeout`, which is directly observable.
  2. An early TShark extraction used `awk` with default field splitting, which collapsed empty
     columns and misaligned request/response classification, making BYE responses appear to exist.
     Replaced with tab-delimited reads of `_ws.col.Info` and CSeq-based classification. A `200 OK`
     I first attributed to a BYE was in fact the next INVITE 2xx retransmission in the backoff
     sequence.
  3. My first scenario probes closed stdin immediately, which triggers the documented EOF shutdown
     before commands are processed, making it look as though refusal envelopes were missing. They
     are not (finding 11).
  4. My first feature-gate probes ran against an unreachable port, where the timeout pre-empted the
     gate check and made the gates look ignored. They are not (finding 9).
- **Loopback capture was unavailable.** `dumpcap` is `root:wireshark` mode 0754 and this user is not
  in the `wireshark` group; `sudo` is forbidden by this review's rules. Rather than rely on sipx's
  own synthesized `--capture` output for protocol claims, findings 1 and 2 were established with a
  purpose-written independent SIP UAC and UAS (plain Python sockets, no sipx code) exchanging real
  datagrams, and only then cross-checked against `--capture`. Both independent peers and sipx-vs-sipx
  runs agree, which rules out my message construction as the cause: sipx's own UAC provokes the same
  2xx retransmission storm and its own BYE goes equally unanswered.
- **`grep` on this machine is shimmed to `ugrep`** by the user's shell configuration. It behaved
  compatibly for every use here, and no finding depends on grep semantics.
- **The shell is zsh**, not the `fish` the environment advertised; timing used
  `date +%s.%N` deltas rather than shell-specific constructs, and signal tests were driven from
  Python `subprocess` so children carried default signal dispositions instead of a shell background
  job's inherited `SIGINT` mask.
- **Bounds and cleanup.** Every call, load and background peer was finite, with `--wait`/`--duration`/
  `--timeout`/`--calls` caps and an outer `timeout(1)`. Harnesses tracked exact PIDs and trapped
  `EXIT`/`INT`/`TERM`; no broad `pkill -f` pattern was used. Ports 5060–5145 on loopback only; no
  traffic left the machine except HTTPS to crates.io, GitHub and the docs site.
- **Timing figures are from a busy, disk-pressured shared machine** (62 GiB RAM with 39 GiB swap in
  use, root filesystem at 96–99 % full throughout). Cold-start, setup-latency and peak-RSS numbers
  should be read as order-of-magnitude, and the single `timed_out` call out of 100 on loopback may
  well be machine noise rather than a product characteristic — I did not repeat the load run enough
  times to separate them.
- All generated evidence, downloads, the consumer crate and both probe implementations were kept in
  a scratch directory outside the reviewed tree and outside the invoking checkout, and removed after
  the run. No untracked file was left in the clone.
