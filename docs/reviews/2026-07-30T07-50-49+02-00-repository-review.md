# Repository review — 2026-07-30T07:50:49+02:00

## Executive assessment

The repository has a notably strong verification baseline: the complete 22-step local gate is
green, every feature combination builds, the advertised minimum Rust version builds all targets,
the dependency policy check is green, and the parser and protocol layers have unusually deliberate
limits and adversarial tests. The sans-I/O boundary of `sipx-sip` and `sipx-sdp` also holds in the
reviewed snapshot.

That baseline does not make the tree release-ready. This review found **eight actionable defects**:
three P1 and five P2. The highest operational risk is in stream-transport lifetime management. Pool
eviction removes bookkeeping without terminating the connection task, and TLS/WebSocket handshakes
are spawned before the pool with neither a deadline nor a concurrency bound. An unauthenticated peer
can therefore keep more live tasks and sockets than the configured connection limit claims to allow.

The current X-39 maturity-report change also remains unsound in two commit shapes. It reads all
index, working-tree, and untracked story changes instead of the snapshot being committed, and it
dates pending facts with the wall clock while committed facts use author dates. Both permit a report
to be green locally and red in a clean checkout.

No P0 issue, committed credential, `unsafe` block, dependency-policy failure, or forbidden I/O in
the sans-I/O core was found.

## Severity model

- **P0** — immediate loss of confidentiality/integrity, remote code execution, or a universally
  broken release path.
- **P1** — remotely triggerable denial of service, a core correctness invariant broken in an
  ordinary workflow, or local verification that can approve a commit known to fail clean CI.
- **P2** — material resource leak, panic, silent subsystem failure, or correctness defect requiring
  a narrower configuration or timing condition.
- **P3** — maintainability, diagnostics, or limited edge behavior without a demonstrated material
  failure.

## Findings

### R-01 — P1 — Pool eviction does not terminate the socket task it claims to close

**Evidence**

- `crates/sipx-transport/src/tcp.rs:267-280` implements idle eviction by removing a `Pooled` value
  from the map.
- `crates/sipx-transport/src/tcp.rs:308-321` does the same LRU removal before registering another
  connection at the configured maximum.
- The only cancellation signal removal creates is closure of the writer channel.
- `crates/sipx-transport/src/tcp.rs:510-564` matches that receiver as
  `Some(bytes) = outgoing.recv()`. Once all senders are dropped, the pattern does not match; the
  branch becomes disabled while the socket read remains pending. The `else` arm therefore does not
  run, and a quiet peer keeps the task and socket alive until the peer closes them.
- `crates/sipx-transport/src/ws.rs:252-303` has the same refutable receive pattern. Its ping branch
  remains live, so an evicted WebSocket can continue indefinitely and continue sending pings.
- `crates/sipx-transport/src/tcp.rs:762-785` tests only that the map becomes empty. It never observes
  EOF at the peer or task termination.
- `docs/specs/sip-transport.md` §8 says the pool is bounded and idle connections are closed. The
  implementation currently bounds map entries, not live connections.

**Failure scenario**

An unauthenticated peer opens more than `max_connections` TCP connections and leaves them quiet. As
new connections arrive, the pool evicts old map entries, but each old pump remains blocked on its
socket. The process can accumulate tasks, sockets, parser buffers, and encrypted-session state well
beyond the advertised bound. The same issue means the periodic idle sweep logs that a connection was
closed when no close occurred.

**Recommendation**

Give every pump an explicit cancellation signal or make channel closure an explicit match arm that
breaks the loop. Make eviction await or otherwise observe shutdown where practical. Add tests that
hold the peer half of a TCP and WebSocket connection, evict the pool entry, and prove the peer sees
closure and the pump terminates. Add a count-above-limit test that observes live sockets, not
`Pool::len()`.

### R-02 — P1 — Pre-pool TLS and WebSocket handshakes have no deadline or concurrency bound

**Evidence**

- `crates/sipx-transport/src/endpoint.rs:740-766` accepts TLS sockets and spawns one task per
  handshake.
- `crates/sipx-transport/src/endpoint.rs:780-798` does the same for WebSocket upgrades.
- `crates/sipx-transport/src/endpoint.rs:817-843` repeats it for secure WebSocket connections.
- These tasks are created before a connection is adopted into `Pool`, so `PoolConfig::max_connections`
  cannot bound them.
- The handshake/upgrade awaits at `endpoint.rs:749`, `endpoint.rs:789`, `endpoint.rs:826`, and
  `endpoint.rs:834` have no timeout. No semaphore, task set, or other concurrency accounting exists
  in the transport source.
- The transport tests cover successful and refused handshakes but do not hold a handshake partially
  open and assert reclamation.

**Failure scenario**

An unauthenticated client repeatedly connects to a TLS, WS, or WSS listener and then sends no
handshake bytes, or sends an incomplete upgrade. The accept loop deliberately keeps accepting and
spawning so one slow peer does not block the next, but every slow peer retains a socket and task
without entering the bounded pool. Resource use therefore grows with the attacker’s connection
count.

**Recommendation**

Put one shared configurable handshake deadline around the complete TLS-plus-upgrade sequence and
hold a bounded permit from accept through adoption. On endpoint shutdown, cancel outstanding
handshakes. Add paused-time tests for a peer that sends nothing, a peer that stalls midway through
TLS, and a peer that sends a partial HTTP upgrade; assert the deadline, permit release, and socket
closure.

### R-03 — P1 — Maturity pending facts are taken from the whole local tree, not the commit snapshot

**Evidence**

- `scripts/maturity.py:260-262` combines `git diff HEAD`, all untracked story files, and the whole
  working-tree diff.
- That data includes staged changes, unstaged changes, and unrelated untracked stories.
- `scripts/test-maturity.py:376-378` stages every fixture change with `git add -A`, so the tests never
  create a selective commit.

**Failure scenario**

Two stories are created locally. A developer stages one story and the generated maturity report but
leaves the second story untracked. Generation counts both stories. After the selective commit, the
second story still exists, so local `--check` remains green; clean CI checks a snapshot containing
only one story and reports drift. The same mismatch applies to an unstaged closure beside a staged
one.

**Recommendation**

Define the pending half as the index snapshot that will be committed: use cached/index diffs and
read new story contents from the index rather than from disk. Treat unstaged and untracked changes as
out of scope for the commit’s report, or refuse generation with a precise message until the intended
story changes are staged. Add fixture tests with two new stories and two closures in which only one
of each is staged, then verify both the dirty post-commit tree and a clean checkout of the commit.

### R-04 — P2 — Pending maturity facts use a date different from the committed history’s date

**Evidence**

- `scripts/maturity.py:318-342` groups committed facts using `%ad`, the commit author date.
- `scripts/maturity.py:344-354` assigns all pending facts to `datetime.date.today()`.
- Tests can backdate commits, but every pending-fact commit path uses the current date and therefore
  does not test an amended historical author date or a midnight boundary.

**Failure scenario**

A report is generated before midnight and committed after midnight. It is green before the commit,
but the fact moves to the next date when read from history. Similarly, amending an older commit while
retaining its author date moves a fact from today’s pending row to the older author-date row. A clean
checkout of the resulting commit is red even though the dirty local tree may continue to mask it.

**Recommendation**

Choose one stable event-date source that exists before the commit and survives it. Suitable designs
include explicit story-event dates in repository data or reporting only complete days; merely
switching between author and committer dates does not remove the before/after-midnight race. Add
tests where generation and commit occur on different dates and where an old commit is amended
without resetting its author date.

### R-05 — P2 — Dropping a conference detaches its participant collectors and keeps sessions alive

**Evidence**

- `crates/sipx-media/src/conference.rs:95-126` spawns one collector per participant. Each collector
  owns an `Arc<MediaSession>` and the shared members map.
- `crates/sipx-media/src/conference.rs:156-164` correctly aborts collectors in explicit `close()`.
- `crates/sipx-media/src/conference.rs:167-172` aborts only the mixer in `Drop`.
- Dropping the collector `JoinHandle`s detaches their tasks; it does not cancel them. The collectors
  can remain blocked in `session.recv()` while retaining the sessions, sockets, and shared map.
- Every conference integration test calls `close()`. By contrast,
  `crates/sipx-media/tests/bridge.rs:254-285` explicitly tests drop cleanup for `Bridge`.

**Failure scenario**

A caller drops a `Conference` without first awaiting `close()`. The mixer stops, but participant
collectors remain alive and retain every session. The public object is gone while media resources can
survive for the rest of the process.

**Recommendation**

Abort every collector in `Drop` without awaiting, then clear synchronous ownership or redesign the
conference around one cancellation token observed by mixer and collectors. Add a drop-without-close
test that proves forwarding stops and all participant/session strong references are released.

### R-06 — P2 — A public endpoint capacity of zero panics during bind

**Evidence**

- `crates/sipx-transport/src/endpoint.rs:47-48` exposes `Config::capacity` as an unrestricted
  `usize`.
- `crates/sipx-transport/src/endpoint.rs:654-655` and `endpoint.rs:686` pass it directly to bounded
  channel constructors, which require a value greater than zero and panic otherwise.
- The same API already normalizes caller-provided capacity in
  `crates/sipx-transport/src/endpoint.rs:534-535`, showing the intended zero-safe convention.
- `bind` returns `Result`, but this invalid public configuration bypasses that error path and
  unwinds instead.

**Failure scenario**

An application builds `Config::new(...)`, sets `capacity = 0` from its own configuration, and awaits
`bind`. Startup panics after sockets/listeners have begun to be created rather than returning a typed
configuration error.

**Recommendation**

Either use a non-zero type, validate all public configuration before any I/O, or consistently raise
zero to one and document that rule. A typed error is preferable where zero is operator input. Add a
test for zero capacity through the public bind path.

### R-07 — P2 — Zero public timing values can kill workers or create a busy loop

**Evidence**

- `crates/sipx-media/src/session.rs:243-284` exposes `packet_duration` and `rtcp_interval` directly.
- `crates/sipx-media/src/session.rs:1686` constructs the send interval from `packet_duration`; a zero
  interval panics in the detached send task after the constructor has returned a session.
- `crates/sipx-media/src/session.rs:2364-2381` repeatedly sleeps for the randomized RTCP interval.
  A zero base produces a zero sleep and a hot loop, including the no-traffic `continue` path.
- `crates/sipx-media/src/conference.rs:77-79` accepts any interval and returns a conference while its
  mixer later panics at `conference.rs:177` for zero.
- `crates/sipx-transport/src/endpoint.rs:76-82` exposes `ws_keepalive`; the connection pump later
  panics at `crates/sipx-transport/src/ws.rs:248` for zero.

**Failure scenario**

Operator-derived zero values create objects successfully, then fail asynchronously: a media session
cannot send, a conference mixer dies, a WebSocket pump dies, or RTCP consumes a core in a loop. In
several cases the caller receives neither a construction error nor task failure and sees only a dead
subsystem.

**Recommendation**

Validate every timing field before spawning any task. Model required non-zero intervals explicitly;
where zero means disabled, use `Option<Duration>` and branch before spawning. Constructors that can
reject configuration should return a typed error. Test zero at every public entry point and assert no
worker was started.

### R-08 — P2 — Failed Opus setup sends and decodes PCMU while labeling the stream as Opus

**Evidence**

- `crates/sipx-media/src/session.rs:160-171` handles an Opus encoder-construction failure by logging
  that the session will send nothing, then returns `Encoding::Direct(Codec::Pcmu)`.
- `crates/sipx-media/src/session.rs:208-216` does the analogous substitution for the decoder.
- Direct encoding and decoding execute that selected codec at `session.rs:184-189` and
  `session.rs:225-230`.
- The RTP payload type still comes from the original session configuration at
  `session.rs:1707-1711`; changing the internal encoder does not renegotiate or relabel it.
- `Config::channels` is a public unrestricted `usize`, while the Opus constructor accepts only its
  supported channel layouts. No test exercises the failure branches.

**Failure scenario**

A media user requests Opus with an invalid channel count. Instead of sending nothing as the log and
comment promise, sipx encodes PCMU bytes under the negotiated Opus payload type. The peer interprets
those bytes as Opus, producing decode failures or noise. Incoming Opus is likewise decoded as PCMU,
which can turn compressed bytes into audible garbage.

**Recommendation**

Reject the media configuration before starting the session, or add explicit disabled encoder and
decoder states whose operations return `None`. Never substitute a codec without negotiation. Add
failure-path tests that assert no RTP is emitted and no audio is delivered for an unsupported channel
layout.

### Architecture and adversarial-input checks

- `sipx-sip` and `sipx-sdp` do not import a runtime, sockets, filesystem access, or a clock read.
  Address value types are used, which does not perform I/O.
- SIP datagram/stream parsing has explicit message, body, and header limits checked before the
  corresponding large allocation.
- The application protocol bounds JSON nesting.
- ICE bounds candidate-pair growth and makes its limit configurable.
- Application-facing queues are generally bounded and load shedding is observable.
- TLS client verification has no disable switch, verifies the intended identity, and redacts key
  material from debug output.
- Capture redaction has extensive cases for authentication and media-key material.

The transport lifetime findings are therefore exceptions to an otherwise consistent boundedness
design, not a repository-wide absence of limits.

## Test and review gaps exposed by the findings

The common pattern is that tests observe bookkeeping or happy-path output but not ownership
termination and alternate repository snapshots:

1. Pool tests assert map length, not socket/task death.
2. Handshake tests complete or fail promptly; none stays partial past a deadline.
3. Maturity fixtures stage everything, so index-versus-worktree behavior is invisible.
4. Maturity fixtures do not move generation and commit across date attribution boundaries.
5. Conference tests always call `close()`, so `Drop` is untested.
6. Public zero-value configurations are absent from endpoint/media/conference tests.
7. Codec-construction failure logs are not tested against actual emitted/decoded media.

Closing those gaps with failing-first tests would prevent each concrete regression class rather than
only fixing the current line.

## Maintainability observations

These are not defect findings, but they raise future review cost:

- `sipx-call/src/call.rs` is approximately 4,661 lines and combines negotiation, dialog state,
  reliable provisional handling, updates, transfer behavior, media setup, and retransmission task
  ownership. Its tests are broad, but changes have a large blast radius.
- `sipx-media/src/session.rs` is approximately 3,580 lines and combines public configuration,
  packet pacing, codec state, RTP/SRTP, RTCP, playback, recording, DTMF, statistics, and worker
  lifecycle. R-07 and R-08 both cross responsibilities inside this file.
- The repository has strong generated-document checks, but X-39 demonstrates that a generator whose
  input includes future commit metadata needs snapshot semantics specified as explicitly as a wire
  protocol.

Good extraction boundaries would be ownership units rather than cosmetic modules: stream task
lifetime, media configuration validation, codec pipeline construction, and report snapshot/date
policy.

## Recommended remediation order

1. Fix R-01 and R-02 together as one transport resource-budget story: explicit task cancellation,
   live-connection accounting, handshake permits, and deadlines.
2. Fix R-03 before treating X-39 as complete; add selective-index clean-checkout tests.
3. Decide the event-date model for R-04 in the maturity specification before changing code.
4. Fix R-05 with drop cleanup and a strong-reference/task-termination test.
5. Add centralized public configuration validation covering R-06 and R-07 before spawning or
   binding.
6. Make codec pipeline construction fallible for R-08; never substitute wire codecs.
7. Run the complete gate, the CI-only soak/fuzz jobs relevant to transport lifetime, and a focused
   connection-flood test before release.

## Final verdict

The repository’s engineering controls are stronger than average and all currently enforced local
checks pass, but **the reviewed snapshot should not be treated as release-ready until the three P1
findings are resolved**. R-01 and R-02 defeat advertised resource bounds under unauthenticated
network behavior. R-03 preserves the exact “local green, clean CI red” class X-39 was meant to close.
The five P2 findings should be scheduled immediately after because they leak sessions, panic or spin
workers, and can put the wrong codec on the wire.
