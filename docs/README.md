## The generated reports

This is the evidence surface: pages that report what has been measured rather than what is
claimed. Every one of them is generated from a source elsewhere in the tree and names its
generator in its own opening lines, so disagreeing with one means changing its source rather
than editing the page.

The list below is generated too. `scripts/check-report-index.py` derives it from the reports that
exist, and the gate is red when one of them is not described here — with what it measures, and
with what it deliberately does not, so that opening a page is not how a reader finds out it is
not a quality claim. That is the point of generating it: a hand-typed list would be right today
and silent on the day a fifth report lands (`X-117`). Where the public site republishes a
report's generated body the entry says so; the file itself stays internal either way.

- **[Stack comparison](comparison.md)** — what choosing sipx wins and what it costs against
  the stacks a reader is actually weighing it against, one confidence tier per cell, plus a
  leaf-level endpoint capability ledger and a signalling-load ladder. **Deliberately not** —
  the comparison is asymmetric: sipx's own column is computed from this repository, and
  every other column is somebody reading someone else's code. The capability ledger is a
  finite discovery gate, not a score, and a stack that was not evaluated on a question says
  so in its own row. Generated by `scripts/comparison-report.py`; its body is also published
  on the site as [reference/comparison](../website/docs/reference/comparison.md).

- **[RFC compliance](compliance.md)** — what sipx implements, what it only parses and what
  it has not started, per RFC and per role, generated from `docs/rfc/registry.toml` and held
  against the parser and the files each entry cites. **Deliberately not** — it cannot check
  that behaviour is *correct*; the tests do that, and each entry points at them. The list is
  bounded on purpose and is not every SIP-related RFC. What it stops is this table drifting
  away from the code. Generated by `scripts/rfc-report.py`; its body is also published on
  the site as [reference/compliance](../website/docs/reference/compliance.md).

- **[Coverage: what the suite executes](coverage.md)** — which lines, branches and functions
  the suite executes, per crate and workspace-wide, as arithmetic over counts recorded by
  `cargo llvm-cov` at a named commit. **Deliberately not** — **no threshold gates the build
  on any number on it**, and a drop fails nothing. It measures what the suite executes, not
  whether executing it proved anything. Generated by `scripts/coverage-report.py`; internal
  to this repository.

- **[Maturity: measured release readiness](maturity.md)** — distance to the release
  predicates, RFC coverage per layer, open work per pillar and filed-versus-closed per day,
  generated from roadmap predicates, story frontmatter and git. **Deliberately not** — it
  does not turn RFC coverage into a weighted release score, and nothing in it measures
  whether the tests are good, only that they pass. Some predicates are attested rather than
  computed, and it names which. Generated by `scripts/maturity.py`; internal to this
  repository.

## Specs vs. designs

They are not the same thing and the distinction matters here.

- A **spec** (`specs/`) is the normative contract for a subsystem: RFC citations, types,
  state tables, timers, and byte-level test vectors. It is written *before* the code and is
  what the tests are derived from. It says what the software must do.
- A **design** (`designs/`) is the record of a decision: why this approach, what was
  rejected, what is still open. It says why the software is shaped the way it is.

An epic normally has both — a design that frames it, and one or more specs it implements.

## Working here

Every contributor — human or agent — starts at [AGENTS.md](../AGENTS.md) → **"Start here"**:
open the [board](stories/README.md), take the top `ready` story by priority, follow the loop,
keep the gate green. New or unscoped work? Create a story first (`/track:story`) so the next
agent inherits the context. After any change to a story's status/priority/title/epic/note, run
`/track:board`. Optional story `areas` are query-only subsystem tags matching crate names, so
`/track:next sipx-rtp` selects media-layer work.
